# 写开发日志（worklog）

每个功能开发 / 问题修复完成后**必须**写一条日志。日志最大价值不在单条，而在**跨需求定期汇总**——集中归档才能定期复盘、找共性、反哺文档与 Skill。

## 归档位置与命名（严格遵守）

```
docs/{项目}/logs/{yyyyMM}/{yyyyMMdd}-{模块代码}-{简短标题}.md
```

- **{项目}**：当前工作所属的项目目录（如 `ioh`、`apple-esim-transfer`、`websheet`）。**先确定项目**：
  - 用户当前会话正在做哪个项目，就用哪个；
  - 若 `docs/{项目}/` 尚不存在 → 先走 `init-project-docs` skill 创建项目文档骨架，再写日志；
  - 判断不了项目属于哪个 → 问用户。
- **月份目录** `yyyyMM`：不存在就先创建（如 `docs/ioh/logs/202607/`）。
- **日期取当天真实日期**：用 `date +%Y%m%d` 取，**不要用上下文里可能过期的日期**（踩过的坑）。
- **模块代码小写**：对应本仓库服务 `orchestration` / `websheet` / `integration` / `device-interface` / `diameter-client` / `config` / `om` / `es-common-lib`。
- 示例：`docs/ioh/logs/202607/20260717-orchestration-转移鉴权修复.md`

## 工作流程

1. 用 `date +%Y%m%d` 取当天日期；确认 `docs/{项目}/logs/{yyyyMM}/` 存在，不存在则 `mkdir -p`。
2. 确定模块代码与一句话标题。
3. 按下方模板写日志文件（**六段，核心是 3/5/6 三段**，没走弯路可省第 3 段但要在文中说明"本次顺利无弯路"）。
4. 更新 `docs/{项目}/logs/README.md` 的状态表（月份 + 日志数）。
5. 完成后回复用户日志路径 + 一句话总结沉淀了什么。

## 日志模板

```markdown
# {yyyyMMdd} {模块} {标题}

## 1. 背景/问题现象
这次做了什么功能，或遇到什么问题（贴关键现象、报错、预期 vs 实际）。

## 2. 方案/根因
最终采用的方案，或问题定位到的最小解释。涉及代码列 `文件:行号`。

## 3. 走过的弯路（有就必须写）
尝试失败的方案 + 为什么失败。AI 跑偏、理解错、考虑不全的地方都记在这。
本次顺利没走弯路就写"无"。

## 4. 效果
性能对比 / 数据验证 / 测试结果，用数据说话，不只写"OK"。

## 5. 经验沉淀（日志最大价值，至少 1 条）
可被同事或未来的自己复用的通用结论。

## 6. 优化建议（反哺项目的抓手）
每个坑对应一条：该补哪份文档 / 加或改哪个 Skill / 加哪条铁律。
```

## 关键要求

- **3、5、6 是灵魂**：弯路 + 经验 + 建议。日志里坑越多，说明文档/Skill/流程越要补。
- **用数据说话**：效果段贴测试结果、对比数据，禁止只写"OK / 已完成"。
- **诚实**：走了弯路就如实写，不粉饰。理想状态是日志"平平无奇"。

## 反模式

- ❌ 把日志写进需求目录散落各处——必须集中到 `docs/{项目}/logs/` 按月归档。
- ❌ 用上下文旧日期当文件名——必须 `date +%Y%m%d` 取当天。
- ❌ 只记流水账不沉淀经验——没有第 5、6 段的日志等于没写。
- ❌ 项目目录不存在就硬写——先走 `init-project-docs` 建骨架。
