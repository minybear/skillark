## 走过的弯路

1. **险些直接覆盖原 README**：zip 内自带一个 `README.md`（讲方法论与用法）。若直接写我的归档 README 会把它冲掉。
   改为先把原 README 改名 `PACK-README.md`，再写新 `README.md`，两份都保留。
2. **Write 工具前置要求**：对「已存在但未读过」的文件直接 Write 会被拒，需先 Read——这是防护机制，归档覆盖场景要先读后写。

## 经验 / 优化建议

1. **设计包之间要核对「同名单表」**：v0.2 的 `sources` 与 v0.1 同名不同构，是跨版本设计最容易踩的坑。
   建议每个新版本的 SQL 草案开头标注「相对上一版本的 ALTER/CREATE 差异」，而不是给整表骨架。
2. **目录约定先对齐再归档**：源包的 `design/sql`、`design/schemas` 与本项目 `sql/`、`contracts/` 命名不一，
   归档时统一可减少后续引用混乱。建议后续设计包直接按本项目约定产出。
3. **「归档即分析」值得固化**：这次在归档时顺手做了内容分析、冲突检测、issue 登记，比单纯解压堆放更有价值。
   可作为后续接收外部设计/资料包的标准动作。
4. **建议下一步**：为 v0.2 Link Bridge 单独建 plan 并优先解决 sources 迁移冲突；按 v0.2→…→v1.0 顺序推进，不跳版
   （来源/修订抽象是 v0.3 聚合、v0.4 审计、v0.5 AI、v0.6 lockfile 的共同前置）。
