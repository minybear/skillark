### 反证修复（失败扩图 F1–F4）
G15 复跑时发现 `windows_environment.rs` 出现 **1 failed**（此前账本是 117 全过），按失败扩图机制处理：

- **F1 复现/最小化**：`copy_probe_reports_acl_denied_parent_as_unwritable` 必现 panic。
- **F2 区分根因**：非功能退化、非权限问题。是测试代码**编码假设错误**——`String::from_utf8(whoami输出).unwrap()`，
  但 `whoami` 在中文 Windows 上以**系统 ANSI 代码页（GBK）**输出「主机名\用户名」（主机名 `desktop-7safuli` 后接中文），
  非合法 UTF-8 → `unwrap` 触发 `FromUtf8Error`。
- **F3 修复根因**：先尝试改用 SID（`whoami /user`，纯 ASCII），但 `icacls` 在本机**不接受 SID**
  （GBK 报错「帐户名与安全标识间无任何映射」）。改回用户名方案，新增 `ansi_bytes_to_string` 辅助：
  用 `MultiByteToWideChar(CP_ACP)`（codepage 0 = 系统 ANSI）把 GBK 字节解码为 UTF-16 再转 String；
  给 `Cargo.toml` 的 `windows-sys` 增加 `Win32_Globalization` feature。
- **F4 回归**：`windows_environment` 2/2 通过；全量 `cargo test --all-targets` 恢复 **117 通过 / 0 失败**。

## 走过的弯路

1. **第一反应是用 SID 绕过编码**——纯 ASCII、与区域无关，看似更稳。但 `icacls` 在本机只认帐户名、拒绝 SID，
   第一次改完反而以另一种方式失败。**教训**：先验证目标工具（icacls）接受什么形式的标识，再决定编码方案。
2. **GBK 乱码会掩盖真实报错**：`icacls` 的 GBK 错误信息经 UTF-8 lossy 显示为乱码，要靠字节模式
   （`�ʻ�...` 即「帐户名/安全标识」）辨认。这印证账本里早记过的「Windows 控制台输出非 UTF-8」坑。
3. **这类 bug 只在中文 Windows 必现**：英文/纯 ASCII 主机名 + 用户名的机器上 `from_utf8` 不会 panic，
   测试长期「看起来是过的」。属于**环境依赖型潜在回归**，日常 CI（多为英文镜像）很难暴露。

## 经验 / 优化建议

1. **Windows 测试处理外部命令输出，永远按 ANSI 代码页解码，不要假设 UTF-8**。
   建议把 `ansi_bytes_to_string` 提升到测试公共 `support` 模块，供所有调用 `whoami`/`icacls`/`net` 等
   原生命令的测试复用（账本早已建议建共享 support helper，可一并落实）。
2. **涉及本机帐户/权限的测试，先确认目标工具接受的标识形式**（用户名 vs SID），再写断言。
3. **环境依赖型回归值得在矩阵里固化**：中文 Windows 是一类真实目标环境，建议在发布前把
   「中文主机名 + 中文用户名」纳入冒烟环境清单，避免此类编码 bug 漏网。
4. `Win32_Globalization` 仅 `cfg(windows)` 生效，不影响 Linux/macOS 交叉编译；已随 clippy+test 通过验证。
