# ISSUE-20260730 · v0.2 设计草案 `sources` 表与 v0.1 已发布库结构冲突

> 状态：open（待 v0.2 立项时处理）
> 严重度：设计冲突（阻塞 v0.2 直接套用草案 SQL，不阻塞 v0.1）
> 关联：`design/v0.2-v1.0/sql/0002_v0_2_link_bridge.sql` vs `design/v0.1/sql/0001_init.sql`

## 现象

归档 v0.2–v1.0 详细设计包时发现：v0.2 增量迁移草案重建的 `sources` 表结构与 v0.1 已发布库的 `sources` **字段不一致**，无法直接套用。

| 来源 | `sources` 字段 |
|---|---|
| v0.1 已上线（`v0.1/sql/0001_init.sql`） | `id, source_type, display_name, base_url, enabled, config_json, created_at, updated_at` |
| v0.2 草案（`v0.2-v1.0/sql/0002_v0_2_link_bridge.sql`） | `id, schema_version, status, raw_json, created_at, updated_at`（通用骨架） |

包内 SQL 已自注：「design skeleton. Fields and foreign keys must be finalized against the implemented domain model.」

## 影响

v0.2 Link Bridge 需要给来源增加 Git 相关身份字段（remote URL / subpath / resolved commit / content hash 等）。
若直接执行草案的 `CREATE TABLE sources(...)`，会与 v0.1 真实库冲突（表已存在且列不同），迁移失败或丢列。

## 建议处理（v0.2 立项时）

1. 对照 v0.1 实际 Domain 类型与 `migrations/`，确定 link-bridge 所需来源字段。
2. 二选一：
   - **ALTER**：在既有 `sources` 上叠加列（remote/subpath/revision/hash），保留 v0.1 数据；或
   - **关联表**：保留 v0.1 `sources` 不动，新建 `source_git_locators`（FK→sources.id）承载 Git 身份。
3. 迁移须在真实 v0.1 库副本上验证幂等 + 数据保留（沿用 v0.1 的 `migration_over_real_*` 测试模式）。
4. 草案 SQL 其余表（`source_revisions` 等）同样需对照实际 Domain 冻结字段/外键后再用。

## 归档备注

本 issue 由「归档即分析」发现，详见 `design/v0.2-v1.0/README.md` 第五节。
