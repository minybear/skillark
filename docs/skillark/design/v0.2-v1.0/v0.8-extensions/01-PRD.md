# SkillArk v0.8 产品需求与推导

> 版本主题：扩展生态版（Ark Extensions）  |  设计状态：Draft  |  基线：前一版本通过发布门禁

## 1. 不可约简的用户结果

**结果：** 新的 Hub、Agent 和扫描规则通过受版本控制、受权限限制、可隔离的扩展接入。

该版本不以“新增页面”或“接入某个 API”为目标。只有当用户能够稳定获得上述结果，且失败不损坏既有 Skill、部署或凭据时，版本才成立。

## 2. 第一性原理推导

### 2.1 起点

- 用户拥有一个外部对象、风险对象、运行目标或版本环境。
- SkillArk 必须把它转化为可验证的内部状态，而不是直接相信来源描述。
- 任何不可逆操作都必须晚于解析、校验、计划与用户确认。
- 当前版本只引入完成结果所需的最小新状态和接口。

### 2.2 推导结论

1. **身份先于操作**：先明确对象是谁、来自哪里、版本是什么，再决定存储或执行。
2. **证据先于结论**：UI 展示的状态必须能追溯到文件、Hash、版本、规则或测试。
3. **失败默认不改变既有状态**：新增流程先落在临时区，成功验证后才提交。
4. **跨版本能力通过接口叠加**：不得绕开 v0.1 的 Skill/Agent/Workspace/Deployment 边界。
5. **概率能力不得拥有确定性副作用**：AI、相似度和风险评分只能影响建议，不能绕过策略。

## 4. MECE 范围

| 维度 | 本版本责任 | 非本版本责任 |
|---|---|---|
| 输入/来源 | 接收并识别本版本定义的输入 | 其他长尾输入留给后续版本或人工流程 |
| 解析/规范化 | 生成版本化内部对象和证据 | 不把无法解析字段编造成确定值 |
| 信任/策略 | 在进入写操作前给出允许、确认、阻断或未知 | 不承诺绝对安全或绝对兼容 |
| 存储/版本 | 保存不可变版本、来源、报告和状态 | 不以目标目录作为唯一真源 |
| 执行/分发 | 通过既有 Plan/Execute 或新增受控执行接口 | 不接受自由文本作为执行指令 |
| 观察/解释 | 展示真实路径、来源、差异、风险和结果 | 不隐藏部分失败或降级状态 |
| 恢复/退出 | 取消、失败清理、回滚、解除管理 | 不静默删除用户修改 |
| 治理/演进 | 版本化 Schema、接口和迁移 | 不提前冻结未经验证的公共 API |

## 5. 功能需求

### 5.1 核心模块

| 模块 | 职责 |
|---|---|
| ExtensionManager | 安装、启停、更新、版本解析与兼容检查。 |
| ExtensionHost | 独立进程运行扩展，限制环境变量、工作目录和生命周期。 |
| CapabilityBroker | 扩展只能通过声明能力调用网络、缓存、只读文件和日志。 |
| ManifestVerifier | 校验 manifest、包 Hash、签名、API 版本和权限。 |
| SDK Contracts | Connector/Agent/Rule 的版本化 JSON-RPC 合约与测试套件。 |
| CrashIsolation | 超时、心跳、资源限制、崩溃禁用与诊断。 |

### 5.2 核心流程

| 流程 | 步骤 |
|---|---|
| 扩展安装 | 下载/本地包 → Hash/签名 → manifest → 权限展示 → 安装但默认禁用高权限扩展。 |
| 调用 | 主程序发送只读请求 → Host → Broker 授权能力 → 结构化响应 → Schema 校验。 |
| 崩溃恢复 | 心跳失败 → 终止 Host → 标记故障 → 主流程降级 → 用户可查看日志/禁用。 |

### 5.3 用户故事

- 作为多 Agent 用户，我可以完成“新的 Hub、Agent 和扫描规则通过受版本控制、受权限限制、可隔离的扩展接入。”。
- 作为谨慎用户，我能看到决定依据，并在写入前取消。
- 作为高级用户，我能固定版本、查看原始证据并导出诊断。
- 作为离线或受限网络用户，我能看到明确降级状态，而不是得到伪成功。

## 6. 明确不做

- 开放付费市场
- 不受限制的原生插件
- 组织成员管理
- 核心流程依赖第三方扩展

## 7. 可证伪版本假设

| 编号 | 可证伪结论 | 样本 | 指标 | 阈值 | 失败决策 |
|---|---|---|---|---|---|
| H-08-01 | 进程外 Host 对搜索/发现类调用的额外 p95 延迟 <100ms。 | 1000 次本地 Connector/Adapter/Rule 调用。 | IPC p95、内存、崩溃隔离。 | p95 <100ms，扩展崩溃不影响主进程。 | 若过慢，批量协议和长连接优化，不退回同进程原生。 |
| H-08-02 | SDK 发布后 8 周内至少产生 5 个可维护第三方扩展。 | 公开示例、文档和测试套件。 | 有效扩展数、作者留存、支持工时。 | ≥5 个，且单扩展平均支持 <4h/周。 | 不足则保持官方内部扩展，不建设市场。 |
| H-08-03 | 权限展示让测试用户对高权限扩展的误安装率下降 ≥50%。 | A/B 安装任务。 | 未阅读权限直接确认比例。 | 下降 ≥50%。 | 否则增加默认禁用、分步授权和首次调用确认。 |

## 8. 验收条件

- 所有 H 假设达到阈值，或范围已按失败决策收缩。
- 关键写操作通过故障注入，无数据丢失与静默覆盖。
- 新增外部依赖存在超时、取消、限流/资源预算和降级策略。
- UI 能展示部分成功、未知和不完整状态。
- 数据迁移、备份与恢复在真实旧数据副本上验证。

## 9. 版本成功指标

- 首次完成该版本核心任务的成功率。
- 从开始到可验证结果的中位时间与 p95。
- 失败后既有状态保持完整的比例（目标 100%）。
- 用户需要绕过策略、手工修复或退出流程的比例。
- 该版本引入的支持工时与高优缺陷数量。
