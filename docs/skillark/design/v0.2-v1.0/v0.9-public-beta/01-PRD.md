# SkillArk v0.9 产品需求与推导

> 版本主题：公开测试版（Public Beta）  |  设计状态：Draft  |  基线：前一版本通过发布门禁

## 1. 不可约简的用户结果

**结果：** 普通用户能在十分钟内获得首次价值；升级和故障不丢数据；问题能通过脱敏诊断定位。

该版本不以“新增页面”或“接入某个 API”为目标。只有当用户能够稳定获得上述结果，且失败不损坏既有 Skill、部署或凭据时，版本才成立。

## 2. 第一性原理推导

### 2.1 起点

- 用户拥有一个外部对象、风险对象、运行目标或版本环境。
- SkillArk 必须把它转化为可验证的内部状态，而不是直接相信来源描述。
- 任何不可逆操作都必须晚于解析、校验、计划与用户确认。
- 当前版本只引入完成结果所需的最小新状态和接口。

### 2.2 推导结论

1. **身份先于操作**：先明确对象是谁、来自哪里、版本是什么，再决定存储或执行。
2. **证据先于结论**：UI 展示的状态必须能追溯到文件、Hash、版本、规则或测试。
3. **失败默认不改变既有状态**：新增流程先落在临时区，成功验证后才提交。
4. **跨版本能力通过接口叠加**：不得绕开 v0.1 的 Skill/Agent/Workspace/Deployment 边界。
5. **概率能力不得拥有确定性副作用**：AI、相似度和风险评分只能影响建议，不能绕过策略。

## 4. MECE 范围

| 维度 | 本版本责任 | 非本版本责任 |
|---|---|---|
| 输入/来源 | 接收并识别本版本定义的输入 | 其他长尾输入留给后续版本或人工流程 |
| 解析/规范化 | 生成版本化内部对象和证据 | 不把无法解析字段编造成确定值 |
| 信任/策略 | 在进入写操作前给出允许、确认、阻断或未知 | 不承诺绝对安全或绝对兼容 |
| 存储/版本 | 保存不可变版本、来源、报告和状态 | 不以目标目录作为唯一真源 |
| 执行/分发 | 通过既有 Plan/Execute 或新增受控执行接口 | 不接受自由文本作为执行指令 |
| 观察/解释 | 展示真实路径、来源、差异、风险和结果 | 不隐藏部分失败或降级状态 |
| 恢复/退出 | 取消、失败清理、回滚、解除管理 | 不静默删除用户修改 |
| 治理/演进 | 版本化 Schema、接口和迁移 | 不提前冻结未经验证的公共 API |

## 5. 功能需求

### 5.1 核心模块

| 模块 | 职责 |
|---|---|
| MigrationManager | 版本化迁移、预检、备份、恢复和迁移历史。 |
| RecoveryManager | 发现未完成 Operation、临时目录和孤儿备份并生成修复计划。 |
| DiagnosticsExporter | 收集版本、状态、错误和必要日志，执行可预览脱敏。 |
| TelemetryService | 明确同意、事件白名单、本地队列、关闭与删除。 |
| PerformanceBudget | 对启动、索引、扫描、部署设置预算和回归门禁。 |
| Onboarding | Agent 扫描、导入示例/真实 Skill、首次分发和成功验证。 |

### 5.2 核心流程

| 流程 | 步骤 |
|---|---|
| 升级 | 预检磁盘/Schema → 自动备份 → 安装签名更新 → 迁移 → smoke test → 成功或自动恢复。 |
| 崩溃恢复 | 启动扫描未完成操作 → 只读诊断 → 生成修复计划 → 用户确认或安全自动清理。 |
| 诊断导出 | 选择范围 → 脱敏预览 → 生成压缩包 → 用户主动分享，不自动上传。 |

### 5.3 用户故事

- 作为多 Agent 用户，我可以完成“普通用户能在十分钟内获得首次价值；升级和故障不丢数据；问题能通过脱敏诊断定位。”。
- 作为谨慎用户，我能看到决定依据，并在写入前取消。
- 作为高级用户，我能固定版本、查看原始证据并导出诊断。
- 作为离线或受限网络用户，我能看到明确降级状态，而不是得到伪成功。

## 6. 明确不做

- 新增大型业务功能
- 公共 Skill 发布平台
- 商业订阅
- 跨设备同步

## 7. 可证伪版本假设

| 编号 | 可证伪结论 | 样本 | 指标 | 阈值 | 失败决策 |
|---|---|---|---|---|---|
| H-09-01 | 80% 的新测试用户能在 10 分钟内完成首次成功分发。 | 至少 50 名未参与设计的 Windows 用户。 | 完成率、中位时间、阻塞点。 | ≥80% 且中位 <10 分钟。 | 未达标冻结发布，修复前三阻塞点。 |
| H-09-02 | 自愿遥测覆盖 ≥30% 活跃用户并定位 ≥70% 的高频失败。 | 四周 Beta。 | 同意率、事件覆盖、可定位缺陷比例。 | ≥30%/≥70%。 | 不足时强化本地诊断，不扩大收集范围。 |
| H-09-03 | 目标规模下核心预算稳定。 | 低配/中配 Windows 与 Mac，500 Skill、10 万索引、100 部署。 | 启动、搜索、验证、内存 p95。 | 达到统一性能基线，连续 20 次无退化 >10%。 | 未达标缩小默认索引/并发并延后发布。 |

## 8. 验收条件

- 所有 H 假设达到阈值，或范围已按失败决策收缩。
- 关键写操作通过故障注入，无数据丢失与静默覆盖。
- 新增外部依赖存在超时、取消、限流/资源预算和降级策略。
- UI 能展示部分成功、未知和不完整状态。
- 数据迁移、备份与恢复在真实旧数据副本上验证。

## 9. 版本成功指标

- 首次完成该版本核心任务的成功率。
- 从开始到可验证结果的中位时间与 p95。
- 失败后既有状态保持完整的比例（目标 100%）。
- 用户需要绕过策略、手工修复或退出流程的比例。
- 该版本引入的支持工时与高优缺陷数量。
