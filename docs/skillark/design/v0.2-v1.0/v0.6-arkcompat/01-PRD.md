# SkillArk v0.6 产品需求与推导

> 版本主题：兼容与可复现版（ArkCompat）  |  设计状态：Draft  |  基线：前一版本通过发布门禁

## 1. 不可约简的用户结果

**结果：** 分发前生成兼容报告；必要转换创建派生版本；项目通过 manifest/lockfile 在新机器恢复相同内容 Hash。

该版本不以“新增页面”或“接入某个 API”为目标。只有当用户能够稳定获得上述结果，且失败不损坏既有 Skill、部署或凭据时，版本才成立。

## 2. 第一性原理推导

### 2.1 起点

- 用户拥有一个外部对象、风险对象、运行目标或版本环境。
- SkillArk 必须把它转化为可验证的内部状态，而不是直接相信来源描述。
- 任何不可逆操作都必须晚于解析、校验、计划与用户确认。
- 当前版本只引入完成结果所需的最小新状态和接口。

### 2.2 推导结论

1. **身份先于操作**：先明确对象是谁、来自哪里、版本是什么，再决定存储或执行。
2. **证据先于结论**：UI 展示的状态必须能追溯到文件、Hash、版本、规则或测试。
3. **失败默认不改变既有状态**：新增流程先落在临时区，成功验证后才提交。
4. **跨版本能力通过接口叠加**：不得绕开 v0.1 的 Skill/Agent/Workspace/Deployment 边界。
5. **概率能力不得拥有确定性副作用**：AI、相似度和风险评分只能影响建议，不能绕过策略。

## 4. MECE 范围

| 维度 | 本版本责任 | 非本版本责任 |
|---|---|---|
| 输入/来源 | 接收并识别本版本定义的输入 | 其他长尾输入留给后续版本或人工流程 |
| 解析/规范化 | 生成版本化内部对象和证据 | 不把无法解析字段编造成确定值 |
| 信任/策略 | 在进入写操作前给出允许、确认、阻断或未知 | 不承诺绝对安全或绝对兼容 |
| 存储/版本 | 保存不可变版本、来源、报告和状态 | 不以目标目录作为唯一真源 |
| 执行/分发 | 通过既有 Plan/Execute 或新增受控执行接口 | 不接受自由文本作为执行指令 |
| 观察/解释 | 展示真实路径、来源、差异、风险和结果 | 不隐藏部分失败或降级状态 |
| 恢复/退出 | 取消、失败清理、回滚、解除管理 | 不静默删除用户修改 |
| 治理/演进 | 版本化 Schema、接口和迁移 | 不提前冻结未经验证的公共 API |

## 5. 功能需求

### 5.1 核心模块

| 模块 | 职责 |
|---|---|
| CapabilityRegistry | 保存 Agent/版本/平台的能力声明与证据来源。 |
| RequirementExtractor | 从 Skill 结构、指令和依赖提取要求，AI 只能提供提示。 |
| CompatibilityAnalyzer | Requirement × Capability → 状态、证据和修复选项。 |
| TransformationEngine | 执行版本化、可预览、可逆的声明式转换，输出 DerivedSkillVersion。 |
| ManifestService | 维护期望的 Skill、来源、目标和策略。 |
| LockfileResolver | 解析不可变 revision/hash，执行 restore/check/update/audit。 |

### 5.2 核心流程

| 流程 | 步骤 |
|---|---|
| 兼容分析 | SkillVersion + AgentInstallation → 提取要求 → 匹配能力 → 原生/可转换/部分/不兼容/未知。 |
| 转换分发 | 用户选择转换 → 预览 patch → 创建派生版本 → ArkGuard 重扫 → 分发，不覆盖原始版本。 |
| 环境恢复 | 读取 manifest/lock → 验证 Schema → 解析来源与 Hash → 下载/缓存 → 校验 → 计划多目标部署。 |

### 5.3 用户故事

- 作为多 Agent 用户，我可以完成“分发前生成兼容报告；必要转换创建派生版本；项目通过 manifest/lockfile 在新机器恢复相同内容 Hash。”。
- 作为谨慎用户，我能看到决定依据，并在写入前取消。
- 作为高级用户，我能固定版本、查看原始证据并导出诊断。
- 作为离线或受限网络用户，我能看到明确降级状态，而不是得到伪成功。

## 6. 明确不做

- 保证所有 Agent 行为一致
- 自动修复任意业务逻辑
- 在线团队后台
- 远程执行环境

## 7. 可证伪版本假设

| 编号 | 可证伪结论 | 样本 | 指标 | 阈值 | 失败决策 |
|---|---|---|---|---|---|
| H-06-01 | Capability Profile 对测试矩阵中的失败原因预测 precision ≥90%。 | 至少 100 个 Skill × 4 Agent × 2 平台组合，记录真实结果。 | 预测 precision/recall、unknown 比例。 | precision ≥90%，unknown ≤20%。 | 未达标则只显示确定性结构差异，不给百分比分数。 |
| H-06-02 | 声明式转换能解决至少 60% 的高频可修复不兼容。 | 从失败矩阵选前 50 个可修复案例。 | 转换后通过率、语义回归失败。 | 通过率 ≥60%，严重语义回归 0。 | 否则限制为建议 Patch，不自动生成派生版本。 |
| H-06-03 | Lockfile 在干净环境恢复内容 Hash 一致率 100%。 | Windows/WSL/macOS 测试机各 20 个项目快照。 | 恢复 Hash 一致率和失败可解释率。 | Hash 100%；失败均有明确缺失依赖。 | 任一静默不一致阻断发布。 |

## 8. 验收条件

- 所有 H 假设达到阈值，或范围已按失败决策收缩。
- 关键写操作通过故障注入，无数据丢失与静默覆盖。
- 新增外部依赖存在超时、取消、限流/资源预算和降级策略。
- UI 能展示部分成功、未知和不完整状态。
- 数据迁移、备份与恢复在真实旧数据副本上验证。

## 9. 版本成功指标

- 首次完成该版本核心任务的成功率。
- 从开始到可验证结果的中位时间与 p95。
- 失败后既有状态保持完整的比例（目标 100%）。
- 用户需要绕过策略、手工修复或退出流程的比例。
- 该版本引入的支持工时与高优缺陷数量。
