# SkillArk v0.2 产品需求与推导

> 版本主题：链接安装版（Link Bridge）  |  设计状态：Draft  |  基线：前一版本通过发布门禁

## 1. 不可约简的用户结果

**结果：** 用户粘贴 Git 仓库或子目录链接，能够预览候选 Skill、固定来源修订、导入、检查更新并安全回滚。

该版本不以“新增页面”或“接入某个 API”为目标。只有当用户能够稳定获得上述结果，且失败不损坏既有 Skill、部署或凭据时，版本才成立。

## 2. 第一性原理推导

### 2.1 起点

- 用户拥有一个外部对象、风险对象、运行目标或版本环境。
- SkillArk 必须把它转化为可验证的内部状态，而不是直接相信来源描述。
- 任何不可逆操作都必须晚于解析、校验、计划与用户确认。
- 当前版本只引入完成结果所需的最小新状态和接口。

### 2.2 推导结论

1. **身份先于操作**：先明确对象是谁、来自哪里、版本是什么，再决定存储或执行。
2. **证据先于结论**：UI 展示的状态必须能追溯到文件、Hash、版本、规则或测试。
3. **失败默认不改变既有状态**：新增流程先落在临时区，成功验证后才提交。
4. **跨版本能力通过接口叠加**：不得绕开 v0.1 的 Skill/Agent/Workspace/Deployment 边界。
5. **概率能力不得拥有确定性副作用**：AI、相似度和风险评分只能影响建议，不能绕过策略。

## 4. MECE 范围

| 维度 | 本版本责任 | 非本版本责任 |
|---|---|---|
| 输入/来源 | 接收并识别本版本定义的输入 | 其他长尾输入留给后续版本或人工流程 |
| 解析/规范化 | 生成版本化内部对象和证据 | 不把无法解析字段编造成确定值 |
| 信任/策略 | 在进入写操作前给出允许、确认、阻断或未知 | 不承诺绝对安全或绝对兼容 |
| 存储/版本 | 保存不可变版本、来源、报告和状态 | 不以目标目录作为唯一真源 |
| 执行/分发 | 通过既有 Plan/Execute 或新增受控执行接口 | 不接受自由文本作为执行指令 |
| 观察/解释 | 展示真实路径、来源、差异、风险和结果 | 不隐藏部分失败或降级状态 |
| 恢复/退出 | 取消、失败清理、回滚、解除管理 | 不静默删除用户修改 |
| 治理/演进 | 版本化 Schema、接口和迁移 | 不提前冻结未经验证的公共 API |

## 5. 功能需求

### 5.1 核心模块

| 模块 | 职责 |
|---|---|
| LinkResolver | 把输入规范化为 RepositoryLocator，不访问业务数据库。 |
| GitSourceAdapter | 获取 refs、归档或浅克隆，并返回不可变 SourceRevision。 |
| RepositoryScanner | 在受限目录内发现 SKILL.md，构建候选项和共享资源边界。 |
| RepositoryCache | 按 remote + revision 缓存，支持 LRU 与完整性校验。 |
| UpdateService | 比较已安装 revision 与远端 revision，生成更新计划。 |
| DiffService | 生成文本/文件树差异；二进制仅显示 Hash 与大小变化。 |

### 5.2 核心流程

| 流程 | 步骤 |
|---|---|
| 链接导入 | 粘贴 URL → 规则解析 → 获取默认 revision → 下载到隔离缓存 → 扫描候选 Skill → 用户选择 → 校验/Hash → 导入 Library。 |
| 更新检查 | 读取 pinned ref → 查询远端 → 获取候选 revision → 下载临时快照 → Diff → 用户确认 → 创建新 SkillVersion → 保留旧版本。 |
| 失败恢复 | 任一步失败只清理本次临时缓存；现有 Library 和 Deployment 不变。 |

### 5.3 用户故事

- 作为多 Agent 用户，我可以完成“用户粘贴 Git 仓库或子目录链接，能够预览候选 Skill、固定来源修订、导入、检查更新并安全回滚。”。
- 作为谨慎用户，我能看到决定依据，并在写入前取消。
- 作为高级用户，我能固定版本、查看原始证据并导出诊断。
- 作为离线或受限网络用户，我能看到明确降级状态，而不是得到伪成功。

## 6. 明确不做

- 多 Hub 聚合搜索
- 任意网页 AI 解析
- 私有仓库 OAuth
- 自动执行依赖命令

## 7. 可证伪版本假设

| 编号 | 可证伪结论 | 样本 | 指标 | 阈值 | 失败决策 |
|---|---|---|---|---|---|
| H-02-01 | 规则解析能正确处理至少 95% 的公开 GitHub 仓库/子目录链接。 | 200 条去重真实链接，覆盖默认分支、tree/blob、尾斜杠、多个 Skill。 | 正确识别 remote/revision/subpath 的比例。 | ≥95%，且 0 次路径越界。 | 低于阈值则只支持明确格式，并把长尾留给 v0.5。 |
| H-02-02 | 更新前 Diff 不会让主要流程明显变慢。 | 30 名内测用户完成 3 次更新任务。 | 中位完成时间、跳过率、误更新率。 | 中位增加时间 <45 秒，误更新为 0。 | 若跳过率高则默认折叠 Diff，但高风险文件强制展示。 |
| H-02-03 | 缓存使重复导入 p95 时间降低至少 50%。 | 20 个 1MB-200MB 仓库，冷/热各 5 次。 | 导入 p95 与磁盘占用。 | 热缓存 p95 降低 ≥50%，缓存命中正确率 100%。 | 未达标则简化为归档缓存，取消复杂 Git object 复用。 |

## 8. 验收条件

- 所有 H 假设达到阈值，或范围已按失败决策收缩。
- 关键写操作通过故障注入，无数据丢失与静默覆盖。
- 新增外部依赖存在超时、取消、限流/资源预算和降级策略。
- UI 能展示部分成功、未知和不完整状态。
- 数据迁移、备份与恢复在真实旧数据副本上验证。

## 9. 版本成功指标

- 首次完成该版本核心任务的成功率。
- 从开始到可验证结果的中位时间与 p95。
- 失败后既有状态保持完整的比例（目标 100%）。
- 用户需要绕过策略、手工修复或退出流程的比例。
- 该版本引入的支持工时与高优缺陷数量。
