# SkillArk v1.0 产品需求与推导

> 版本主题：稳定正式版（Stable）  |  设计状态：Draft  |  基线：前一版本通过发布门禁

## 1. 不可约简的用户结果

**结果：** 核心 Schema、Lockfile、扩展 API、支持矩阵和发布流程稳定；用户可预期升级、故障处理与安全响应。

该版本不以“新增页面”或“接入某个 API”为目标。只有当用户能够稳定获得上述结果，且失败不损坏既有 Skill、部署或凭据时，版本才成立。

## 2. 第一性原理推导

### 2.1 起点

- 用户拥有一个外部对象、风险对象、运行目标或版本环境。
- SkillArk 必须把它转化为可验证的内部状态，而不是直接相信来源描述。
- 任何不可逆操作都必须晚于解析、校验、计划与用户确认。
- 当前版本只引入完成结果所需的最小新状态和接口。

### 2.2 推导结论

1. **身份先于操作**：先明确对象是谁、来自哪里、版本是什么，再决定存储或执行。
2. **证据先于结论**：UI 展示的状态必须能追溯到文件、Hash、版本、规则或测试。
3. **失败默认不改变既有状态**：新增流程先落在临时区，成功验证后才提交。
4. **跨版本能力通过接口叠加**：不得绕开 v0.1 的 Skill/Agent/Workspace/Deployment 边界。
5. **概率能力不得拥有确定性副作用**：AI、相似度和风险评分只能影响建议，不能绕过策略。

## 4. MECE 范围

| 维度 | 本版本责任 | 非本版本责任 |
|---|---|---|
| 输入/来源 | 接收并识别本版本定义的输入 | 其他长尾输入留给后续版本或人工流程 |
| 解析/规范化 | 生成版本化内部对象和证据 | 不把无法解析字段编造成确定值 |
| 信任/策略 | 在进入写操作前给出允许、确认、阻断或未知 | 不承诺绝对安全或绝对兼容 |
| 存储/版本 | 保存不可变版本、来源、报告和状态 | 不以目标目录作为唯一真源 |
| 执行/分发 | 通过既有 Plan/Execute 或新增受控执行接口 | 不接受自由文本作为执行指令 |
| 观察/解释 | 展示真实路径、来源、差异、风险和结果 | 不隐藏部分失败或降级状态 |
| 恢复/退出 | 取消、失败清理、回滚、解除管理 | 不静默删除用户修改 |
| 治理/演进 | 版本化 Schema、接口和迁移 | 不提前冻结未经验证的公共 API |

## 5. 功能需求

### 5.1 核心模块

| 模块 | 职责 |
|---|---|
| CompatibilityContract | 冻结 Schema、Lockfile、Extension API 与迁移规则。 |
| SupportMatrix | 记录平台/Agent/版本/模式的 tested、supported、preview、unsupported。 |
| ReleaseTrain | RC、Stable、Hotfix、LTS 分支与签名发布自动化。 |
| SecurityResponse | 漏洞接收、分级、修复 SLA、撤销规则/扩展和公告。 |
| LifecycleManager | 版本支持窗口、弃用通知、迁移文档和兼容测试。 |
| ProductMetrics | 在隐私边界内验证价值、稳定性和支持负载。 |

### 5.2 核心流程

| 流程 | 步骤 |
|---|---|
| 稳定发布 | RC 冻结 → 完整门禁 → 签名构建 → 分阶段发布 → 指标观察 → 全量或回滚。 |
| 安全热修复 | 报告 → 严重性判定 → 私有修复 → 签名 Hotfix → 公告/规则撤销 → 复盘。 |
| 弃用 | 至少一个次版本预警 → 替代路径 → 兼容期 → Major 版本移除。 |

### 5.3 用户故事

- 作为多 Agent 用户，我可以完成“核心 Schema、Lockfile、扩展 API、支持矩阵和发布流程稳定；用户可预期升级、故障处理与安全响应。”。
- 作为谨慎用户，我能看到决定依据，并在写入前取消。
- 作为高级用户，我能固定版本、查看原始证据并导出诊断。
- 作为离线或受限网络用户，我能看到明确降级状态，而不是得到伪成功。

## 6. 明确不做

- 大型 SaaS 后台
- 公共付费市场
- 组织级权限与结算
- 移动端

## 7. 可证伪版本假设

| 编号 | 可证伪结论 | 样本 | 指标 | 阈值 | 失败决策 |
|---|---|---|---|---|---|
| H-10-01 | v1.0 RC 在四周内满足 crash-free sessions ≥99.5%，核心操作成功率 ≥99%。 | 分阶段 RC，至少 500 活跃设备周。 | 崩溃率、导入/部署/更新/恢复成功率。 | ≥99.5%/≥99%，无数据损坏。 | 不达标继续 RC，不发布 Stable。 |
| H-10-02 | 12 个月支持周期可在预计维护容量内完成。 | 基于 Beta 缺陷、安全事件和发布工时建模。 | 每月维护工时、未处理高优缺陷。 | 维护占用 ≤总开发时间 40%，P0 按 SLA 清零。 | 超过则缩短矩阵或调整支持周期，不增加承诺。 |
| H-10-03 | Extension API v1 可实现三个不同类型扩展且无需私有逃生接口。 | 官方+第三方 Connector、Agent、Scanner 各一。 | 私有接口调用数、兼容测试。 | 0 个未声明主程序接口依赖。 | 否则继续标 experimental，不冻结 v1。 |

## 8. 验收条件

- 所有 H 假设达到阈值，或范围已按失败决策收缩。
- 关键写操作通过故障注入，无数据丢失与静默覆盖。
- 新增外部依赖存在超时、取消、限流/资源预算和降级策略。
- UI 能展示部分成功、未知和不完整状态。
- 数据迁移、备份与恢复在真实旧数据副本上验证。

## 9. 版本成功指标

- 首次完成该版本核心任务的成功率。
- 从开始到可验证结果的中位时间与 p95。
- 失败后既有状态保持完整的比例（目标 100%）。
- 用户需要绕过策略、手工修复或退出流程的比例。
- 该版本引入的支持工时与高优缺陷数量。
