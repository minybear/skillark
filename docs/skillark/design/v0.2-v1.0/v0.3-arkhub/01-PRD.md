# SkillArk v0.3 产品需求与推导

> 版本主题：多 Hub 聚合版（ArkHub）  |  设计状态：Draft  |  基线：前一版本通过发布门禁

## 1. 不可约简的用户结果

**结果：** 用户在一个搜索入口中查看多个来源的标准化结果，识别重复与原始来源，并按需缓存安装包。

该版本不以“新增页面”或“接入某个 API”为目标。只有当用户能够稳定获得上述结果，且失败不损坏既有 Skill、部署或凭据时，版本才成立。

## 2. 第一性原理推导

### 2.1 起点

- 用户拥有一个外部对象、风险对象、运行目标或版本环境。
- SkillArk 必须把它转化为可验证的内部状态，而不是直接相信来源描述。
- 任何不可逆操作都必须晚于解析、校验、计划与用户确认。
- 当前版本只引入完成结果所需的最小新状态和接口。

### 2.2 推导结论

1. **身份先于操作**：先明确对象是谁、来自哪里、版本是什么，再决定存储或执行。
2. **证据先于结论**：UI 展示的状态必须能追溯到文件、Hash、版本、规则或测试。
3. **失败默认不改变既有状态**：新增流程先落在临时区，成功验证后才提交。
4. **跨版本能力通过接口叠加**：不得绕开 v0.1 的 Skill/Agent/Workspace/Deployment 边界。
5. **概率能力不得拥有确定性副作用**：AI、相似度和风险评分只能影响建议，不能绕过策略。

## 4. MECE 范围

| 维度 | 本版本责任 | 非本版本责任 |
|---|---|---|
| 输入/来源 | 接收并识别本版本定义的输入 | 其他长尾输入留给后续版本或人工流程 |
| 解析/规范化 | 生成版本化内部对象和证据 | 不把无法解析字段编造成确定值 |
| 信任/策略 | 在进入写操作前给出允许、确认、阻断或未知 | 不承诺绝对安全或绝对兼容 |
| 存储/版本 | 保存不可变版本、来源、报告和状态 | 不以目标目录作为唯一真源 |
| 执行/分发 | 通过既有 Plan/Execute 或新增受控执行接口 | 不接受自由文本作为执行指令 |
| 观察/解释 | 展示真实路径、来源、差异、风险和结果 | 不隐藏部分失败或降级状态 |
| 恢复/退出 | 取消、失败清理、回滚、解除管理 | 不静默删除用户修改 |
| 治理/演进 | 版本化 Schema、接口和迁移 | 不提前冻结未经验证的公共 API |

## 5. 功能需求

### 5.1 核心模块

| 模块 | 职责 |
|---|---|
| ConnectorHost | 统一调度 Connector，隔离认证、分页、游标和速率限制。 |
| RegistryNormalizer | 把来源字段映射到最小公共模型，同时保留 raw_metadata。 |
| SyncScheduler | 按来源独立增量同步，支持游标、退避、中断恢复和手动刷新。 |
| SearchIndex | SQLite FTS5 + 结构化筛选，结果与来源状态解耦。 |
| DedupeEngine | 通过 canonical repository、content hash、fork relation 和相似度建立候选簇。 |
| CacheManager | 元数据、预览、包缓存三级存储与配额淘汰。 |

### 5.2 核心流程

| 流程 | 步骤 |
|---|---|
| 来源同步 | 调度 → Connector 分页读取 → 规范化 → upsert → 更新游标 → 独立提交来源状态。 |
| 统一搜索 | FTS/筛选 → 聚合重复簇 → 展示主项与来源差异 → 安装时解析到 SourceRevision。 |
| 离线模式 | 网络不可用 → 使用最后成功索引 → 明确显示数据时间 → 仅安装已有包缓存。 |

### 5.3 用户故事

- 作为多 Agent 用户，我可以完成“用户在一个搜索入口中查看多个来源的标准化结果，识别重复与原始来源，并按需缓存安装包。”。
- 作为谨慎用户，我能看到决定依据，并在写入前取消。
- 作为高级用户，我能固定版本、查看原始证据并导出诊断。
- 作为离线或受限网络用户，我能看到明确降级状态，而不是得到伪成功。

## 7. 可证伪版本假设

| 编号 | 可证伪结论 | 样本 | 指标 | 阈值 | 失败决策 |
|---|---|---|---|---|---|
| H-03-01 | 三个首批 Connector 的核心字段归一完整率 ≥90%。 | 每来源随机 500 条，人工标注 name/description/source/version/license/install locator。 | 必填字段完整率和错误映射率。 | 完整率 ≥90%，错误映射 <2%。 | 不足字段保留来源专属展示，不进入统一筛选。 |
| H-03-02 | 统一搜索比逐站搜索降低任务时间至少 40%。 | 20 名用户完成指定 Skill 查找和来源比较。 | 任务完成时间、页面切换数、正确来源选择率。 | 时间降低 ≥40%，正确率不下降。 | 若无明显收益，v0.3 收缩为来源收藏与快速跳转。 |
| H-03-03 | 10 万条元数据下常用查询 p95 <1 秒。 | 固定 10 万条多语言数据，低配 Windows 机器。 | 启动、关键词、筛选、分页 p95。 | 常用查询 p95 <1 秒，内存增量 <250MB。 | 改用增量 FTS/分页，取消高成本实时相似搜索。 |

## 8. 验收条件

- 所有 H 假设达到阈值，或范围已按失败决策收缩。
- 关键写操作通过故障注入，无数据丢失与静默覆盖。
- 新增外部依赖存在超时、取消、限流/资源预算和降级策略。
- UI 能展示部分成功、未知和不完整状态。
- 数据迁移、备份与恢复在真实旧数据副本上验证。

## 9. 版本成功指标

- 首次完成该版本核心任务的成功率。
- 从开始到可验证结果的中位时间与 p95。
- 失败后既有状态保持完整的比例（目标 100%）。
- 用户需要绕过策略、手工修复或退出流程的比例。
- 该版本引入的支持工时与高优缺陷数量。
