# 写需求计划（plan）

单个需求的分析 / 方案 / 计划 / 测试放 `docs/{项目}/plan/`（任务层），随需求推进记录"做什么 / 做到哪了"。这是多会话协作的桥梁——不同会话不共享对话历史，靠读同一批 plan 文档对齐。

## 目录结构

```
docs/{项目}/plan/{yyyyMMdd}-{模块}-{需求名}/
    00-需求概览.md      # 一句话目标 + 背景 + 边界（做什么/不做什么）
    01-需求分析.md      # 澄清表：AI 疑问 → 澄清结论（先对齐再动手）
    02-方案设计.md      # 多方案对比表 + 定稿（AI 给选项，人拍板）
    03-开发计划.md      # 任务拆分 + 依赖 + 每步验收点
    04-测试方案.md      # 范围 + 类型（单测/集成/API）+ 覆盖要求
    05-测试用例.md      # 具体用例：正常/边界/异常/并发
```

- **{项目}**：当前所属项目目录（如 `ioh`、`websheet`）。目录不存在先走 `init-project-docs` 建骨架。
- 目录名日期用 `date +%Y%m%d` 取当天；模块代码小写（同 worklog）。
- **小需求不必凑齐 6 份**：核心是 `01-需求分析` + `02-方案设计`，其余按需。

## 工作流程

1. `date +%Y%m%d` 取当天，建目录 `docs/{项目}/plan/{yyyyMMdd}-{模块}-{需求名}/`。
2. 按需产出文档。优先级：`00`（总要）→ `01` 澄清 → `02` 方案 → `03/04/05` 落地。
3. 在 `docs/{项目}/plan/README.md` 的需求状态表登记一行（需求 / 模块 / 阶段 / 状态）。
4. 回复用户 plan 目录路径 + 已产出哪几份。

## 各文档要点

**01-需求分析.md —— 澄清表**（先对齐再动手，需求含糊一分后面返工十分）

```markdown
| AI 提出的疑问 | 澄清结论 |
|---|---|
| 超时时长是否可配置？ | 是，配置项 xxx，默认 30 |
```

**02-方案设计.md —— 多方案对比 + 定稿**（AI 给 2~3 个候选，人拍板，不默认单方案）

```markdown
| 维度 | A 方案 | B 方案 | C 方案 |
|---|---|---|---|
| 优点 | | | |
| 缺点 | | | |
| 工作量 | | | |
定稿：选 X（理由）
```

**03-开发计划.md —— 任务拆分 + 验收点**

```markdown
| # | 任务 | 验收点 |
|---|---|---|
```

## 关键要求

- **先文档后代码**：plan 没对齐就写代码是大忌。
- **多方案对比**：逼 AI 把权衡摊开，单方案常藏未言明的假设。
- **澄清结果落盘**：澄清结论写进 01，作为后续所有会话的共同上下文。
